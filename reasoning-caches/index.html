Cache the Reasoning, Not the Answer

A frontier model solves a problem once. A builder model turns that reasoning into Python that runs on a CPU, with a 1B model only to read the input. On a cache hit the big model is never called, and the query costs 16–291× less. Those savings grow with how hard the problem is. They shrink with everything that makes a task hard to program.

Reading: CPU-ARC: Agentic Reasoning Caching for on-CPU Reasoning Reuse · arXiv 2611.09891 · Nov 2026

The betFinding a solution and running it are two different jobs

The paper rests on two observations, and both are easiest to see on one small problem.

Ask a model how many positive divisors 196 has. It factors 196 = 2² × 7², recalls that the count is the product of (exponent + 1), and answers (2+1)(2+1) = 9. Now ask about 144, or reword the question. The reasoning steps don’t change; only the numbers that pass through them do. Yet a language model pays for the whole chain of thought again every time.

  1. Once a problem is solved, running the solution needs almost no language model. What’s left is computation: factor, add one, multiply.
  2. One reasoning trace covers a whole class of problems. Every problem that is equirational to the original (solvable by the same reasoning) can reuse it.

So the authors cache the reasoning as a parameterised program, not the answer. They call the result an agentic reasoning cache (ARC).

The mechanismFunctions that find each other by meaning

An ARC entry is a network of semantic functions. Each is a plain Python callable that takes a Context and returns a dict whose keys are natural-language descriptions. Nothing is referenced by name. Inputs are fetched by description, and other functions are called by describing what you want done:

def check_rotation(ctx):
    narrate(ctx, "Checking if a valid rotation maps blue vertices to red")
    B = load(ctx, "the blue vertex set B", d_type=list)
    n = load(ctx, "the vertex count n", d_type=int)
    r = do(ctx, "Compute the difference set D(B) for subset B with modulus n",
           payloads={"the set of vertices B": B, "the modulus n": n})
    D = load(r, "difference set", d_type=set, ctx=ctx)
    valid = set(range(n)) - D
    return {"valid rotation exists": len(valid) > 0, "valid k values": sorted(valid)}

load and do resolve by vector search over a 300M-parameter embedding model, so a function written for one problem can be found and reused by another without anyone knowing its name. lm and extract call the small target model for the bits that really are language: classification, pulling a value out of text, converting a messy value to a Python type. narrate writes the human-readable trace that becomes the explanation.

Three models play three roles. The source (Claude Opus 4.5) is the expensive intelligence being cached. The builder (also Opus) writes the cache. The target (Haiku 4.5 at first, then a fine-tuned Llama 3.2 1B) is the only model used when the cache runs.

Once a cache stops changing it can be compiled: every do and load lookup is resolved once and replaced with a direct call or a dictionary read. What’s left is a standalone Python file with no embedding model and no vector store, which you can read, version and ship like any other code.

What it boughtFrontier accuracy, two orders of magnitude cheaper per hit

The cache matches or beats the model it was built from on seven of eight benchmarks, and holds above 90% when problems are reworded, re-numbered, or both. The authors explain the AIME gains (83.3 → 93.3 on ’25) by code not making the arithmetic slips the source makes in its final steps. There is a less flattering explanation too, which comes up in the caveats.

The arithmeticSavings grow with difficulty, because the cache side stays flat

The intuitive guess is that savings should fall as tasks get harder. The table says the opposite: AIME saves 262–291×, GSM8K only 16×. The reason is in what each side of the ratio pays for. The source pays for every reasoning token, about 4,700 output tokens on an AIME problem against 390 on GSM8K. The cache pays for parameter extraction and some CPU time, roughly $0.0004 whether the code underneath is two lines of arithmetic or a modular search.

Building is relatively cheaper for hard problems too: 12× a source call for AIME, 84× for GSM8K, because a long trace often collapses into a short program. Every entry has a break-even point:

net saving per entry = hits × (source cost − cache cost) − build cost

The paper reports about 13 matching queries to pay back an AIME entry and about 90 for GSM8K. The calculator below lets you set the one thing the paper doesn’t measure: how often an entry actually gets hit.

What it really depends onHow much of the task a normal program can do

Difficulty is the wrong axis. The method swaps LLM reasoning for code, so it pays exactly as much as code can take over. That splits into three separate questions, and each limits something different.

Solution is code
Limits cost and correctness. Arithmetic, search and set operations run on the CPU for nothing and never slip. Steps that need judgment become lm() calls to a 1B model. On GPQA the target model writes about 4,500 output tokens per query against 76 on AIME, and savings drop from 291× to 38×. Knowledge isn’t automatically “not code”: in a narrow problem class the builder hard-codes constants and tables.
Same procedure
Limits coverage. A task can be fully programmable and still need a different program per input. An entry only covers inputs that follow the reasoning path the source model’s single trace took. The paper’s parameter changes are filtered to stay on that path, so this is never tested.
Input is parseable
Limits whether a query hits at all. The 1B model has to pull clean parameters out of free text. Numbers, lists and named entities extract well; a long email thread doesn’t. Extraction is already the largest share of run-time cost in Appendix C.

The best case is a task that is hard to work out but becomes a fixed program over clearly extractable parameters. That describes competition maths, and a lot of enterprise agent work where the same instructions get applied to a stream of similar payloads, which is where the authors say they’re headed.

The worst caseNot “no savings”, but confident wrong answers

Invert all three properties and add rarity (judgment at every step, a different procedure per instance, unstructured input, tasks that seldom repeat) and every query misses. You pay for building and for a lookup on every request, and save nothing. That is a loss, but a visible and limited one.

The harmful case is the false hit: a query that looks like a cached problem but needs different reasoning. It might have a parameter outside the range the code assumed, or hit a case the source trace never took (an obtuse angle where the trace only ever saw acute ones), or swap “at least one” for “exactly one”. The embedding clears the threshold, extraction succeeds, the code runs, and out comes a well-narrated wrong answer. An LLM might have noticed something was off; a program just runs. And because the fallback only catches misses and crashes, nothing routes the error back.

A quieter version of the same problem: rules that change. Tax brackets, pricing policies and API behaviour get frozen into the cached functions, which keep applying last quarter’s rules correctly and confidently. The worst fit overall is varied, judgment-heavy, rarely repeated work where a wrong answer costs more than a slow one.

Read before you citeWhat the evaluation doesn’t show

Not what it sounds likeThis isn’t reasoning-as-memory, and “neuralware” isn’t either

The title suggests reasoning traces stored as notes and retrieved into a model’s context for later tasks, as a kind of memory. The paper calls that modular caching and argues against it: even a perfect retrieval still needs a full LLM generation to read the notes and reason again, and nothing guarantees the model uses them correctly. ARC retrieves code to run, and on a hit the big model is never called. That’s the whole trade: far less flexibility, in exchange for a hundredfold cost cut and an artifact you can audit.

“Neuralware”, in the closing section, is a claim about where models sit in the stack. Today the LLM is the top layer, where the thinking happens. The authors imagine a library of cached semantic functions taking that place, with neural models pushed down to a support layer that parses, extracts and converts, the way firmware sits under applications. The LLM isn’t given a memory. It’s demoted.

What to do MondayThe takeaway

If you run an agent endpoint that applies the same instructions to a steady stream of similar payloads, this is worth a prototype. Log the traffic for a few weeks, cluster it, and look for clusters whose answers are a fixed procedure over a handful of extractable values. Those are your cacheable endpoints, and a per-query saving of 20–300× is large enough to survive a lot of pessimism in the paper’s numbers.

Before you ship it, add the missing piece of the loop: a check on hits, not just misses. That could be range checks generated from the builder’s Phase 3 validity analysis and enforced at run time, a sampled audit of hits against the frontier model, or both. Then measure the two numbers the paper doesn’t report, hit rate and false-hit rate, on your own traffic. Those decide whether the method pays off, not the benchmark table.
